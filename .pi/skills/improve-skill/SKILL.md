# Skill 改善

Skill を長いプロンプトとしてではなく、明確な契約を持つ小さなサービスとして改善する。

## 起動条件

次の依頼でだけ使う。

- Skill の改善、分割、レビュー、運用設計を明示的に求められた
- `SKILL.md` のトリガー、実行手順、失敗処理、ディレクトリ構成を見直したい

単なる Skill の利用依頼では使わない。対象の Skill が指定されていない場合は、先に対象パスを確認する。

## 必須の監査

1. 対象ディレクトリと `SKILL.md`、既存の `scripts/`、`references/`、`assets/` を確認する。
2. `SKILL.md` から、メタデータ、起動条件、コア手順、停止条件だけを抽出する。
3. 次を判定する。
   - description が「いつ使うか」を具体的に示しているか
   - 実行可能な処理を文章だけで代替していないか
   - 外部変更、権限、確認ゲート、失敗時の扱いが明記されているか
   - API 詳細、長い例、テンプレートが本体に混在していないか
4. `scripts/validate-skill.sh <skill-dir>` を実行し、構造とメタデータの機械的な不備を確認する。
5. 必要な変更だけを行い、既存の公開動作と命名を維持する。動作を変える場合は変更理由を記録する。
6. `git diff --check` と、対象に実行可能コードがあればその最小テストを実行する。

## 推奨ディレクトリ構成

```text
<skill>/
├── SKILL.md                 # 契約、トリガー、コア手順、停止条件
├── scripts/                 # 決定的な処理、検証、変換、外部コマンドの薄いラッパー
├── references/              # API 仕様、詳細な境界条件、運用 runbook
└── assets/                  # 利用者に渡すテンプレート、スキーマ、固定データ
```

不要なディレクトリは作らない。文章だけで済む詳細は `references/`、再現性が必要な処理は `scripts/` に移す。スクリプトは入力、終了コード、標準出力・標準エラーを定義し、秘密情報をログに出さない。

## 実行ゲート

- 読み取りと分析は、対象と範囲が確定していれば実行する。
- ファイル変更、外部サービス、Git、課金、送信、削除は、対象・入力・影響を表示して確認を得る。
- 入力不足、対象の曖昧さ、権限不足、検証失敗では推測して続行せず停止する。
- スクリプトの非ゼロ終了を成功として報告しない。エラー内容と安全な次の手順を示す。

## 完成条件

- descriptionに明示的なトリガーと非トリガーがある
- `SKILL.md` は短く、実行順序と停止条件を追跡できる
- 決定的な処理はスクリプトまたは既存ツールに委譲されている
- 詳細仕様・テンプレート・境界条件の所在がリンクされている
- 正常系だけでなく入力不備、失敗終了、権限・確認ゲートを検証している

改善後は、変更したファイル、実行した検証、未解決の制約を報告する。
