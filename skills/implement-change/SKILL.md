# Implement a Change

1. Establish the requested outcome and observable acceptance criteria. For non-trivial work, start `task`; do not invent a detailed plan before repository evidence exists.
2. Acquire only the context needed to identify the relevant boundary. Use `context.find` when the location is unknown, then structural `context` actions for concrete source targets. Expand retrieval only when the current evidence is insufficient. Prefer one targeted observation over repeated broad reads, batch independent observations with `multi_tool_use.parallel`, constrain output, and diagnose tool errors before retrying.
3. Keep the current plan disposable. Record a `task.checkpoint` when new evidence changes the intended implementation, not after every tool call.
4. Apply the smallest coherent mutation. For supported existing source, prefer `code`: reuse a continuation when `context` already produced one, otherwise use the exact path/text edit form when it identifies one unique change. Do not call `context` only to make `code` available. Use ordinary file editing for new files and unsupported languages; source-based configuration and generated content follow the runtime's supported-language route.
5. Use `delegate` only for a self-contained workstream with independent acceptance criteria. The child works in an isolated worktree and branch. Its report or process exit is not proof of correctness; inspect and verify the branch before integration.
6. Run the narrowest existing checks that can falsify the change, then broaden with risk. Use `verify.run` for executable existing tests, compiler/typechecker/linter checks, and structural audits. Use `verify.record` only for supporting observations made elsewhere, such as CI, user feedback, review-agent findings, or agent-authored tests. A reported check is not a substitute for an executed check when the check can be run locally.
7. Review the resulting diff for scope, accidental changes, stale comments, secrets, broken contracts, and unnecessary complexity. When the change may affect agreement between implementation, documentation, tests, schemas, configuration, examples, migrations, or generated contracts, use `consistency-review` to give an independent reviewer the current `task.review_context` packet and resolve concrete findings.
8. If the task began from a clean Git workspace and has verified intended changes, use `git-workflow` to commit those task changes before completion unless the user explicitly asked to leave them uncommitted. Treat this clean-start completion contract as authorization for the task commit only; never include unrelated paths. If commits are explicitly forbidden, leave the task active, blocked, or stopped rather than falsely closing it.
9. Call `task.finish` only when the requested outcome is supported by the workspace, at least one successful check executed through `verify.run` has no unresolved latest failure, any `task.review_context` request has a matching successful independent `review_agent` report for the final workspace, and the clean-start Git completion contract is satisfied. If evidence is insufficient, continue, block, or stop rather than converting completed steps into a completion claim.

Keep architecture and product decisions with the parent until repository evidence resolves them. A worker may implement a resolved decision; it should not silently widen the contract.
