# Implement a Change

Pi Kit's `context`, `code`, `task`, and `verify` tools are Codemode-exposed. Invoke them from `codemode` scripts; use `delegate` and `terminal` directly when those boundaries are needed.

1. Establish the requested outcome and observable acceptance criteria. Pi Kit may announce a `robust` control policy in the system prompt. Under `robust`, start `task` for non-trivial work; under `lean` or when no robust policy is announced, work directly by default and start `task` only when durable external state or strict completion gating is specifically useful, such as long-running work, compaction, multi-worker coordination, or recovery. Once a task starts, its completion contract is authoritative regardless of the current policy. Do not invent a detailed plan before repository evidence exists.
2. Acquire only the context needed to identify the relevant boundary. Use `context.find` when the location is unknown, then structural `context` actions for concrete source targets. Expand retrieval only when the current evidence is insufficient. Prefer one targeted observation over repeated broad reads, batch independent observations in `codemode` when useful, constrain output, and diagnose tool errors before retrying.
3. Keep the current plan disposable. When a task is active, record a `task.checkpoint` only when new evidence changes the intended implementation, not after every tool call. Without an active task, keep this state in the ordinary working context rather than creating task state merely to mirror the model's plan.
4. Apply the smallest coherent mutation. For supported existing source, prefer `code`: reuse a continuation when `context` already produced one, otherwise use the exact path/text edit form when it identifies one unique change. Do not call `context` only to make `code` available. Use ordinary file editing for new files and unsupported languages; source-based configuration and generated content follow the runtime's supported-language route.
5. Use `delegate` only for a self-contained workstream with independent acceptance criteria. The child works in an isolated worktree and branch. Its report or process exit is not proof of correctness; inspect and verify the branch before integration.
6. Run the narrowest existing checks that can falsify the change, then broaden with risk. When a task is active, use `verify.run` for executable existing tests, compiler/typechecker/linter checks, and structural audits because `task.finish` trusts executed verification provenance. Without an active task, run the same repository checks through the ordinary shell or `terminal` path and do not start a task solely to route verification through `verify`. Use `verify.record` only when an active task needs supporting observations made elsewhere, such as CI, user feedback, review-agent findings, or agent-authored tests.
7. Review the resulting diff for scope, accidental changes, stale comments, secrets, broken contracts, and unnecessary complexity. When a task is active and the change may affect agreement between implementation, documentation, tests, schemas, configuration, examples, migrations, or generated contracts, use `consistency-review` to give an independent reviewer the current `task.review_context` packet and resolve concrete findings. Without an active task, review the final project state directly and do not start a task solely to manufacture review provenance.
8. If an active task began inside a Git worktree and has verified intended changes, use `git-workflow` to commit those task changes before completion unless the user explicitly asked to leave them uncommitted. This completion contract authorizes only task-local paths; never include pre-existing or unrelated dirty work. If no task is active, follow the user's and repository's ordinary Git policy; there is no Pi Kit commit gate. If commits are explicitly forbidden in a Git-managed active task, leave the task active, blocked, or stopped rather than falsely closing it.
9. When a task is active, call `task.finish` only when the requested outcome is supported by the workspace, at least one successful check executed through `verify.run` has no unresolved latest failure, any `task.review_context` request has a matching successful independent `review_agent` report for the final workspace, and any Git-managed task changes have been committed. Without an active task, report completion from the final workspace and executed checks without creating a synthetic task lifecycle. If evidence is insufficient, continue, block, or stop rather than converting completed steps into a completion claim.

Keep architecture and product decisions with the parent until repository evidence resolves them. A worker may implement a resolved decision; it should not silently widen the contract.
